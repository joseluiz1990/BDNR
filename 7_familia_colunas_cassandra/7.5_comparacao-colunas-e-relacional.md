# 7.5 Comparação: banco de família de colunas e banco relacional

Nos materiais anteriores, o histórico de chamados foi modelado no Cassandra. Este material coloca o mesmo problema ao lado do modelo relacional, para mostrar o que se ganha e o que se perde em cada escolha.

A pergunta deste material é: **quando vale a pena abrir mão da flexibilidade do modelo relacional em troca da distribuição do Cassandra?**

Os comandos SQL são apresentados apenas para comparação, porque o laboratório não tem um banco relacional para os alunos. Os comandos CQL devem ser executados no DbGate, no keyspace criado em 7.2, com os dados das seções 3, 4 e 7 daquele material. Substitua `ana_silva` pelo seu identificador.

## 1. De que "banco de colunas" estamos falando

A expressão "banco orientado a colunas" é usada para duas tecnologias diferentes:

| Aspecto | Relacional tradicional | Família de colunas | Colunar analítico |
|---|---|---|---|
| Exemplos | PostgreSQL, MySQL, SQL Server | Cassandra, ScyllaDB, HBase | ClickHouse, Amazon Redshift, BigQuery |
| Organização física | Linha a linha | Linhas agrupadas por partição | Cada coluna armazenada separadamente |
| Operação típica | Transações e consultas variadas | Muitas escritas e leituras por chave | Somas e médias sobre milhões de linhas |

Este material compara a segunda coluna, que é o modelo do Cassandra, com a primeira.

## 2. O mesmo problema nos dois modelos

O sistema precisa responder a duas perguntas:

| Código | Pergunta |
|---|---|
| Q1 | Qual é o histórico de um chamado, do evento mais recente ao mais antigo? |
| Q2 | Quais chamados um atendente recebeu em determinado dia? |

### Modelo relacional

O ponto de partida são as entidades e seus relacionamentos. Cada fato fica em um único lugar:

```sql
CREATE TABLE atendente (
    id    integer PRIMARY KEY,
    nome  text NOT NULL,
    email text NOT NULL UNIQUE
);

CREATE TABLE chamado (
    protocolo    text PRIMARY KEY,
    titulo       text NOT NULL,
    prioridade   text NOT NULL CHECK (prioridade IN ('baixa', 'media', 'alta')),
    atendente_id integer NOT NULL REFERENCES atendente (id),
    aberto_em    timestamptz NOT NULL
);

CREATE TABLE evento (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    protocolo   text NOT NULL REFERENCES chamado (protocolo),
    ocorrido_em timestamptz NOT NULL,
    tipo        text NOT NULL,
    autor       text NOT NULL,
    descricao   text
);

CREATE INDEX idx_evento_chamado ON evento (protocolo, ocorrido_em DESC);
CREATE INDEX idx_chamado_atendente ON chamado (atendente_id, aberto_em DESC);
```

As duas perguntas são respondidas a partir dessas tabelas:

```sql
-- Q1
SELECT ocorrido_em, tipo, autor
FROM evento
WHERE protocolo = 'CH101'
ORDER BY ocorrido_em DESC;

-- Q2
SELECT c.aberto_em, c.protocolo, c.titulo, c.prioridade
FROM chamado c
JOIN atendente a ON a.id = c.atendente_id
WHERE a.nome = 'bruno'
  AND c.aberto_em >= '2026-11-03' AND c.aberto_em < '2026-11-04'
ORDER BY c.aberto_em DESC;
```

### Modelo de família de colunas

O ponto de partida são as perguntas. Cada uma tem sua tabela, com os dados já prontos para a resposta:

| Pergunta | Tabela | Chave primária |
|---|---|---|
| Q1 | `eventos_por_chamado` | `((protocolo), ocorrido_em, evento_id)` |
| Q2 | `chamados_por_atendente_dia` | `((atendente, dia), aberto_em, protocolo)` |

```sql
-- Q1
SELECT ocorrido_em, tipo, autor
FROM bdnr_ana_silva.eventos_por_chamado
WHERE protocolo = 'CH101';

-- Q2
SELECT aberto_em, protocolo, titulo, prioridade
FROM bdnr_ana_silva.chamados_por_atendente_dia
WHERE atendente = 'bruno' AND dia = '2026-11-03';
```

As consultas ficam parecidas, mas o trabalho mudou de lugar. No relacional, o banco combina os dados **na leitura**. No Cassandra, a aplicação organiza os dados **na escrita**.

## 3. Visão geral

| Aspecto | Relacional | Família de colunas (Cassandra) |
|---|---|---|
| Ponto de partida | Entidades e relacionamentos | Consultas da aplicação |
| Repetição de dados | Evitada pela normalização | Aceita como decisão de projeto |
| Papel da chave primária | Identificar a linha | Identificar, distribuir e ordenar |
| Combinação de tabelas | `JOIN` | Inexistente; a tabela já traz a resposta |
| Filtros | Qualquer coluna; índices melhoram o custo | Restritos à chave primária |
| Integridade | Garantida pelo banco | Responsabilidade da aplicação |
| Transações | Várias linhas e tabelas, com ACID | Limitadas |
| Crescimento típico | Servidor maior; distribuição exige soluções adicionais | Mais nós no cluster |
| Falha de um servidor | Depende da arquitetura de failover | As demais réplicas continuam atendendo |
| Mudança nas consultas | Geralmente uma nova consulta ou índice | Geralmente uma nova tabela e carga dos dados |



### Atender a uma nova pergunta

O gestor pede: "chamados resolvidos por prioridade em cada semana".

| Etapa | Relacional | Cassandra |
|---|---|---|
| Solução | Uma consulta com `JOIN` e `GROUP BY` | Uma tabela nova, particionada por semana e prioridade |
| Dados antigos | Já estão disponíveis | Precisam ser copiados para a tabela nova |
| Dados futuros | Nada a alterar | A aplicação precisa passar a gravar também na tabela nova |
| Custo de manutenção | Talvez um índice novo | Mais uma tabela para manter coerente |

Essa é a principal limitação prática do modelo: **consultas que não foram previstas custam caro**. Se as perguntas mudam o tempo todo, o relacional leva vantagem.

## 4. Escala e disponibilidade

| Situação | Relacional | Cassandra |
|---|---|---|
| Carga de leitura cresce | Réplicas de leitura ou servidor maior | Mais nós |
| Carga de escrita cresce | Servidor maior; depois, particionamento ou soluções distribuídas | Mais nós, com redistribuição automática das faixas de tokens |
| Queda do servidor principal | Failover para uma réplica, com possível interrupção | Sem servidor principal; as demais réplicas atendem |
| Vários datacenters | Possível, com arquitetura específica | Previsto no próprio modelo de replicação |
| Consistência | Forte, em uma instância | Ajustável por operação |

Essas diferenças são tendências, e não regras absolutas. Bancos relacionais também podem ser replicados e particionados, e existem bancos SQL distribuídos. O Cassandra, por sua vez, exige um cluster com vários nós e pessoas que saibam operá-lo, um custo que não se justifica em sistemas pequenos.

### E o desempenho?

Não é correto dizer que um deles é sempre mais rápido. O resultado depende do formato da carga:

| Operação | Comportamento esperado |
|---|---|
| Leitura de uma partição conhecida no Cassandra | Custo previsível, mesmo com a tabela crescendo |
| Leitura por índice no relacional | Muito eficiente em tabelas bem indexadas, no limite de um servidor |
| Escrita no Cassandra | Grava de forma sequencial, sem procurar a linha antiga |
| Consulta com `JOIN` e filtros variados | Possível no relacional; precisa ser preparada com antecedência no Cassandra |

Os exercícios desta aula não medem desempenho. Uma comparação justa exigiria os mesmos dados, a mesma carga e o mesmo hardware.

## 5. Como escolher

| Pergunta sobre o sistema | Aponta para relacional | Aponta para Cassandra |
|---|---|---|
| As consultas são conhecidas e estáveis? | Mudam com frequência | Sim, e são poucas |
| Há muitas operações envolvendo várias entidades? | Sim | Não |
| Regras de integridade são críticas? | Sim | Podem ficar na aplicação |
| O volume cabe em um servidor? | Sim | Não, ou está perto do limite |
| As escritas são intensas e contínuas? | Moderadas | Sim |
| O sistema pode parar quando um servidor falha? | Pode haver uma breve interrupção | Precisa continuar operando |
| Os dados são alterados depois de gravados? | Com frequência | Raramente, como eventos e históricos |

Os dois modelos também podem conviver. No sistema de chamados, os cadastros e as regras de atendimento podem ficar em um banco relacional, enquanto o histórico de eventos, volumoso e previsível, fica no Cassandra.

| Sistema | Escolha provável | Motivo |
|---|---|---|
| Acadêmico: matrículas, notas e pré-requisitos | Relacional | Muitos relacionamentos e regras de integridade |
| Financeiro: movimentação entre contas | Relacional | Transações envolvendo várias linhas |
| Telemetria de milhares de sensores | Cassandra | Escrita contínua e leitura por sensor e período |
| Histórico de reprodução em streaming | Cassandra | Grande volume e consulta por usuário |
| Loja virtual de pequeno porte | Relacional | Volume modesto e consultas variadas |

1. Liste três consultas que o sistema precisa responder sobre as leituras dos sensores e proponha a chave primária da tabela de cada uma.
2. Decida se agendamentos e prontuários ficariam no relacional ou no Cassandra. Justifique usando o quadro da seção 9.
3. Escolha uma regra de integridade do sistema. Explique como ela seria garantida em cada modelo.
4. O veterinário pede uma nova tela, com a média de temperatura por raça. Compare o trabalho necessário nos dois modelos.
