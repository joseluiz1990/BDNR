# 5.1 Preparação do laboratório

O módulo aplica os conceitos de replicação e sharding do módulo 4. A prática começa pela montagem de um replica set em uma VPS e segue pelo Compass, com um banco próprio por aluno no conjunto compartilhado.

## Sequência inicial

1. Acompanhar [5.1.1 Montagem de um replica set na VPS](5.1.1_montagem-replica-set-na-vps.md): processos, portas, diretórios, autenticação e inicialização.
2. Passar para o `rs0` já configurado na VPS do professor. Os alunos não precisam de SSH nem repetem a inicialização.
3. Criar um banco com parte do próprio nome, como `lab5_rs_ana_silva`.
4. Inserir dados pelo conjunto e observar as cópias nos três nós, conforme a prática 5.2.

```text
rs0 compartilhado
  27017 -> lab5_rs_ana_silva + lab5_rs_bruno_lima
  27018 -> cópias dos mesmos bancos
  27019 -> cópias dos mesmos bancos
```

Os papéis primary/secondary podem mudar entre as portas. Cada aluno cria seu banco uma única vez pelo conjunto; os demais membros recebem as cópias automaticamente.

## Roteiro de 3 horas

| Etapa | Minutos |
|---|---:|
| Conexões e diagnóstico | 20 |
| Escrita e observação das cópias | 35 |
| Eleição coordenada | 25 |
| Intervalo | 10 |

Os 180 minutos acima pressupõem a infraestrutura disponível para os testes. Para incluir a demonstração de montagem, reserve mais 40 a 60 minutos ou divida o módulo em dois encontros: montagem e replicação no primeiro; eleição e sharding no segundo. Os alunos acompanham a administração e implementam individualmente seus bancos na VPS compartilhada.

## 3. Ambiente adicional para sharding

Os membros de `rs0` mantêm cópias dos mesmos dados; eles não são três shards. O sharding usa um ambiente separado, na mesma VPS:

| Componente | Porta | Nome interno | Configuração | Acesso pelo Compass |
|---|---:|---|---|---|
| Roteador | 27100 | `router` | Processo `mongos` | Sim, uso normal |
| Shard A | 27101 | `shard-a` | Replica set `rsShardA`, um membro, `shardsvr` | Sim, conexão direta para leitura |
| Shard B | 27102 | `shard-b` | Replica set `rsShardB`, um membro, `shardsvr` | Sim, conexão direta para leitura |
| Config server | 27103 | `cfg` | Replica set `rsConfig`, um membro, `configsvr` | Não, só rede interna |

São quatro processos adicionais. Os shards de um membro permitem demonstrar distribuição, mas não toleram a perda de seu processo. As eleições são estudadas no `rs0` de três membros.

```text
Compass -> rs0 -> 27017 / 27018 / 27019

Compass -> mongos:27100 -> rsShardA:27101
                       -> rsShardB:27102
           mongos consulta rsConfig:27103
```

Cada `mongod` tem diretório de dados exclusivo. Na VPS, os quatro processos rodam em contêineres Docker (imagem `mongo:8.0`) no mesmo projeto do `rs0`, em `/docker/mongo-aulas`, e compartilham o keyfile de autenticação interna.

### Quadro de configuração

| Serviço | Opções de inicialização |
|---|---|
| Shard A | `mongod --shardsvr --replSet rsShardA --port 27101` |
| Shard B | `mongod --shardsvr --replSet rsShardB --port 27102` |
| Config server | `mongod --configsvr --replSet rsConfig --port 27103` |
| Roteador | `mongos --configdb rsConfig/cfg:27103 --port 27100` |

Todos usam também `--bind_ip_all` e `--keyFile`; os `mongod` limitam o cache com `--wiredTigerCacheSizeGB 0.25`.

Os processos se encontram pelos nomes internos da rede Docker (`cfg`, `shard-a`, `shard-b`). Por isso a configuração do cluster registra esses nomes, e não o domínio público. Os alunos não precisam resolvê-los: conectam pelo roteador ou por conexão direta às portas publicadas.

### Inicialização lógica dos novos conjuntos: professor

Os serviços precisam estar iniciados com suas funções corretas. Execute uma vez em cada conjunto ainda não inicializado, com autorização administrativa.

No config server, porta 27103:

```javascript
rs.initiate({
  _id: "rsConfig", configsvr: true,
  members: [{ _id: 0, host: "cfg:27103" }]
})
```

No shard A, porta 27101:

```javascript
rs.initiate({
  _id: "rsShardA",
  members: [{ _id: 0, host: "shard-a:27101" }]
})
```

No shard B, porta 27102:

```javascript
rs.initiate({
  _id: "rsShardB",
  members: [{ _id: 0, host: "shard-b:27102" }]
})
```

Aguarde cada primary e confira `rs.status()`.

As contas existem em dois níveis. As criadas pelo roteador ficam no config server e valem para as conexões ao `mongos`. Cada shard tem também contas locais, usadas apenas nas conexões diretas às portas 27101 e 27102. Em ambos os casos, a exceção de localhost permite criar só o primeiro usuário; os demais são criados por uma sessão autenticada. Na conexão direta, a conta precisa também do papel `directShardOperations` (MongoDB 8.0).

Na sessão administrativa do roteador:

```javascript
sh.addShard("rsShardA/shard-a:27101")
sh.addShard("rsShardB/shard-b:27102")
db.adminCommand({ listShards: 1 })
db.hello()
```

Devem aparecer dois shards e `msg: "isdbgrid"` no roteador. As operações dos alunos sobre dados particionados passam pelo `mongos`.

Não execute `rs.initiate()` em `rs0`, que já foi informado como conjunto existente. Não desative autenticação para contornar erros.

Para ampliar a redundância do cluster de sharding, use três membros por shard e três config servers: nove `mongod` e pelo menos um `mongos`, além do `rs0` separado. Todos na mesma VPS continuam sujeitos à mesma falha de máquina.
