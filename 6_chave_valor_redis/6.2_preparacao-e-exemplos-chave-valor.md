## 2. Testar a conexão e entender o espaço de chaves

```redis
PING
ACL WHOAMI
```

Respostas esperadas: `PONG` e `aluno`. Não use `use banco` como no MongoDB. Nesta aula, todos usam o banco lógico padrão da conexão e separam os dados por prefixos de chave. Um banco lógico numérico do Redis também não equivale a isolamento de acesso por aluno.

Confira as restrições da conta:

```redis
CONFIG GET maxmemory
```

A resposta é um erro `NOPERM`: a ACL da conta `aluno` bloqueia comandos administrativos. As configurações podem ser consultadas pelo comando de informações:

```redis
INFO memory
INFO persistence
```

Em `INFO memory`, localize `maxmemory_human:128.00M` e `maxmemory_policy:allkeys-lru`. Em `INFO persistence`, localize `aof_enabled:1`. Compare com a tabela da seção 5 do material 6.1.

Antes de começar, consulte apenas seu prefixo:

```redis
SCAN 0 MATCH bdnr:ana_silva:* COUNT 100
```

O retorno contém um cursor e uma lista de chaves. Se o cursor retornado não for zero, repita `SCAN` com esse cursor até retornar zero. `COUNT` é uma sugestão de trabalho por chamada; uma página vazia não garante que a iteração terminou. A varredura pode retornar duplicatas e não é um snapshot consistente sob alterações concorrentes.

Sem `MATCH`, a varredura também traz as chaves dos colegas e os dados de exemplo do Redis Insight (`sample_bicycle:...`, `sample_session:...`). Por isso, filtre sempre pelo seu prefixo. `KEYS bdnr:ana_silva:*` daria o mesmo resultado em uma instância pequena, mas percorre todas as chaves de uma vez e bloqueia o servidor durante a busca. Em produção, prefira `SCAN`.

No Browser do Redis Insight, a visualização em árvore agrupa as chaves pelos dois-pontos, como se fossem pastas. É só uma forma de exibição: para o Redis, `bdnr:ana_silva:mensagem` continua sendo um único nome de chave.

A conta `aluno` não consegue executar `FLUSHALL`, `FLUSHDB` nem `SWAPDB`. Ela consegue, porém, apagar ou sobrescrever qualquer chave, inclusive a de um colega. Para reiniciar exemplos, apague somente as chaves explicitamente usadas por você.

## 3. String: gravar, consultar e remover

```redis
SET bdnr:ana_silva:mensagem "Central de suporte"
GET bdnr:ana_silva:mensagem
TYPE bdnr:ana_silva:mensagem
EXISTS bdnr:ana_silva:mensagem
```

Observe `OK`, o texto gravado, o tipo `string` e a existência `1`. O formato visual da resposta varia entre clientes.

Para relacionar com o limite de memória da instância, veja quantos bytes a chave ocupa:

```redis
MEMORY USAGE bdnr:ana_silva:mensagem
```

O valor inclui o nome da chave e estruturas internas, por isso é maior que o texto gravado. O número exato pode variar entre versões.

Atualize o mesmo valor:

```redis
SET bdnr:ana_silva:mensagem "Atendimento iniciado"
GET bdnr:ana_silva:mensagem
```

A chave continua sendo a mesma. Agora remova:

```redis
DEL bdnr:ana_silva:mensagem
GET bdnr:ana_silva:mensagem
EXISTS bdnr:ana_silva:mensagem
```

Após a remoção, `GET` indica ausência, normalmente `(nil)`, e `EXISTS` retorna `0`.

## 4. Sessão temporária e TTL

Crie uma sessão de demonstração com validade de 120 segundos:

```redis
SET bdnr:ana_silva:sessao:demo01 "usuario101" EX 120
GET bdnr:ana_silva:sessao:demo01
TTL bdnr:ana_silva:sessao:demo01
```

O TTL deve estar entre 0 e 120 logo após a escrita. Ele depende do tempo decorrido, portanto não registre um número fixo como resposta obrigatória.

Reduza a validade para um teste rápido:

```redis
EXPIRE bdnr:ana_silva:sessao:demo01 15
TTL bdnr:ana_silva:sessao:demo01
```

Aguarde mais de 15 segundos e execute:

```redis
GET bdnr:ana_silva:sessao:demo01
TTL bdnr:ana_silva:sessao:demo01
```

Espere ausência e TTL `-2`. Compare com uma chave sem expiração:

```redis
SET bdnr:ana_silva:preferencia:idioma "pt-BR"
TTL bdnr:ana_silva:preferencia:idioma
```

| TTL | Interpretação |
|---|---|
| Zero ou positivo | Segundos restantes; zero indica proximidade da expiração |
| -1 | A chave existe e não tem prazo de expiração |
| -2 | A chave não existe |

O prazo pertence à chave. Um `SET` comum que sobrescreve a chave remove o TTL anterior, salvo uso de opções que o preservem. Para renovar um cache, informe `EX` novamente. Uma sessão de demonstração não implementa login completo nem gera um token seguro para uma aplicação real.

## 5. Contador de acessos

Prepare um estado conhecido apenas para seu contador:

```redis
SET bdnr:ana_silva:contador:acessos 0
INCR bdnr:ana_silva:contador:acessos
INCR bdnr:ana_silva:contador:acessos
INCRBY bdnr:ana_silva:contador:acessos 5
GET bdnr:ana_silva:contador:acessos
```

Resultados dos incrementos: `1`, `2` e `7`. O valor final é `7`, representado como string. Esses valores pressupõem uma única execução da sequência.

`INCR` faz o incremento atomicamente no servidor e também inicializa uma chave numérica inexistente. Ele retorna erro quando a string não representa um inteiro válido. Reiniciar com `SET ... 0` apaga a contagem anterior; faça isso apenas na preparação do exercício.

## 6. Hash: resumo estruturado de um chamado

```redis
HSET bdnr:ana_silva:chamado:CH101 protocolo CH101 status aberto prioridade alta atendente bruno
HGET bdnr:ana_silva:chamado:CH101 status
HGETALL bdnr:ana_silva:chamado:CH101
TYPE bdnr:ana_silva:chamado:CH101
```

O tipo será `hash`. `HSET` informa o número de campos novos, não uma confirmação booleana: na primeira execução são quatro; ao atualizar um campo existente, pode retornar zero.

```redis
HSET bdnr:ana_silva:chamado:CH101 status em_andamento
HINCRBY bdnr:ana_silva:chamado:CH101 interacoes 1
HGETALL bdnr:ana_silva:chamado:CH101
```

Em uma execução inicial, `interacoes` passa a `1`. Repita o incremento e observe a mudança. `HGETALL` não fornece uma ordem obrigatória de campos.

Experimente o comando de tipo incorreto:

```redis
GET bdnr:ana_silva:chamado:CH101
```

Espere `WRONGTYPE`: `GET` é para string, enquanto essa chave contém um hash. Volte a usar `HGET` ou `HGETALL`.

## 7. Ranking de atendentes

Para iniciar o ranking de exemplo do zero, remova somente essa chave sua:

```redis
DEL bdnr:ana_silva:ranking:atendentes
ZADD bdnr:ana_silva:ranking:atendentes 12 bruno 8 carla 15 diego
ZRANGE bdnr:ana_silva:ranking:atendentes 0 -1 REV WITHSCORES
```

A ordem inicial decrescente é Diego 15, Bruno 12 e Carla 8. Os índices começam em zero; `-1` indica o último elemento. Membros são únicos: um novo `ZADD` para Bruno altera sua pontuação, sem criar outro Bruno.

Após cinco novos atendimentos de Carla:

```redis
ZINCRBY bdnr:ana_silva:ranking:atendentes 5 carla
ZSCORE bdnr:ana_silva:ranking:atendentes carla
ZRANGE bdnr:ana_silva:ranking:atendentes 0 1 REV WITHSCORES
```

Carla terá 13 e estará em segundo lugar. A última consulta retorna os dois primeiros: Diego e Carla. A pontuação aqui representa uma contagem didática, não uma avaliação completa da qualidade do atendimento.

## 8. Cache miss, preenchimento e cache hit

O próximo experimento simula manualmente o trabalho da aplicação. Não existe sincronização automática entre os comandos Redis e MongoDB apresentados.

Use esta ficha como fonte de referência inicial:

| Protocolo | Cliente | Status na fonte |
|---|---|---|
| CH101 | Cliente 101 | aberto |
| CH102 | Cliente 102 | em_andamento |

Comece removendo apenas a chave de cache do exemplo:

```redis
DEL bdnr:ana_silva:cache:chamado:CH101
GET bdnr:ana_silva:cache:chamado:CH101
```

A ausência representa um cache miss. Consulte a ficha e preencha o cache com o status encontrado:

```redis
SET bdnr:ana_silva:cache:chamado:CH101 "aberto" EX 600
GET bdnr:ana_silva:cache:chamado:CH101
TTL bdnr:ana_silva:cache:chamado:CH101
```

O segundo acesso encontra `aberto`: é um cache hit. A chave guarda apenas o status, não o documento completo. Os 600 segundos são um valor de demonstração, não um prazo recomendado universalmente.

## 9. Produzir e corrigir um valor desatualizado

Execute estas etapas em sequência, antes da expiração. Se o cache já expirou, refaça o preenchimento da seção anterior e registre que ocorreu um miss.

1. Na ficha de referência, altere CH101 para `resolvido`.
2. Consulte o Redis sem alterar o cache:

```redis
GET bdnr:ana_silva:cache:chamado:CH101
```

A resposta continua `aberto`, embora a fonte esteja em `resolvido`. A alteração da fonte não atualiza automaticamente o cache.

3. Invalide a chave depois de confirmar a atualização da fonte:

```redis
DEL bdnr:ana_silva:cache:chamado:CH101
GET bdnr:ana_silva:cache:chamado:CH101
```

4. Simule uma nova consulta à fonte e reconstrua o cache:

```redis
SET bdnr:ana_silva:cache:chamado:CH101 "resolvido" EX 600
GET bdnr:ana_silva:cache:chamado:CH101
```

| Etapa | Fonte | Redis | Interpretação |
|---|---|---|---|
| Após preenchimento | aberto | aberto | Cache preenchido |
| Após alterar somente a fonte | resolvido | aberto | Valor desatualizado |
| Após invalidar | resolvido | ausente | Próximo acesso terá miss |
| Após reconstruir | resolvido | resolvido | Novo resumo disponível |

O experimento observa valores e ciclo de vida. Ele não mede uma diferença de desempenho entre Redis e MongoDB. Para medir desempenho seria necessário controlar cliente, rede, dados e carga.



## 10. Repetição e limpeza

Reexecutar `INCR`, `HINCRBY` e `ZINCRBY` acrescenta ao valor existente. Não espere os mesmos resultados numéricos de uma primeira execução sem preparar os valores de partida. Chaves com TTL podem desaparecer durante a aula.

Para encerrar, consulte seu prefixo com `SCAN` e remova apenas as chaves que deseja descartar, indicando seus nomes explicitamente:

```redis
DEL bdnr:ana_silva:sessao:demo01 bdnr:ana_silva:preferencia:idioma
DEL bdnr:ana_silva:contador:acessos bdnr:ana_silva:chamado:CH101
DEL bdnr:ana_silva:ranking:atendentes bdnr:ana_silva:cache:chamado:CH101
```

Um retorno zero pode significar que a chave já não existia. Não use limpeza global na instância compartilhada.
