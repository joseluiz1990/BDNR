# 6.4 Prática: distribuição de chaves com Redis Cluster

Nos materiais 6.2 e 6.3, todas as chaves ficaram em uma única instância Redis. Esta prática usa um Redis Cluster, em que as chaves são divididas entre três primários, cada um com uma réplica. É o equivalente, no modelo chave-valor, ao cluster particionado do material 5.3.

A pergunta desta prática é: se o nome da chave decide onde ela é armazenada, como a modelagem de chaves afeta a distribuição e as operações com várias chaves?

## 3. Da chave ao slot

O slot de uma chave é `CRC16(nome) mod 16384`. O cálculo depende apenas do nome, não do valor nem do tipo. Consulte o slot das chaves usadas em 6.2:

```redis
CLUSTER KEYSLOT bdnr:ana_silva:sessao:demo01
CLUSTER KEYSLOT bdnr:ana_silva:contador:acessos
CLUSTER KEYSLOT bdnr:ana_silva:chamado:CH101
CLUSTER KEYSLOT bdnr:ana_silva:ranking:atendentes
```

Para `ana_silva`:

| Chave | Slot | Nó (papéis iniciais) |
|---|---:|---|
| `bdnr:ana_silva:sessao:demo01` | 16330 | `redis-c3` |
| `bdnr:ana_silva:contador:acessos` | 9524 | `redis-c2` |
| `bdnr:ana_silva:chamado:CH101` | 6854 | `redis-c2` |
| `bdnr:ana_silva:ranking:atendentes` | 6293 | `redis-c2` |

Com seu identificador, os números serão outros. Registre os seus e use a tabela da seção 2 para descobrir o nó de cada chave. Chaves com nomes parecidos podem cair em slots e nós diferentes: o prefixo comum `bdnr:ana_silva:` não agrupa nada.

## 4. Operações com uma chave

Grave os mesmos dados de 6.2, agora no cluster:

```redis
SET bdnr:ana_silva:sessao:demo01 "usuario101" EX 300
SET bdnr:ana_silva:contador:acessos 0
INCR bdnr:ana_silva:contador:acessos
HSET bdnr:ana_silva:chamado:CH101 protocolo CH101 status aberto prioridade alta
ZADD bdnr:ana_silva:ranking:atendentes 12 bruno 8 carla 15 diego
```

```redis
GET bdnr:ana_silva:sessao:demo01
TTL bdnr:ana_silva:sessao:demo01
HGETALL bdnr:ana_silva:chamado:CH101
ZRANGE bdnr:ana_silva:ranking:atendentes 0 -1 REV WITHSCORES
```

Os comandos e as respostas são iguais aos da instância única, embora as chaves estejam em nós diferentes. O Redis Insight conhece o mapa de slots e envia cada comando ao primário certo. Um cliente que não conhece o mapa recebe `MOVED`, como o professor demonstra na seção 7.

No Browser do Redis Insight, filtre por `bdnr:ana_silva:*`. O Browser reúne as chaves de todos os primários em uma única lista. É a visão lógica do cluster, como a contagem feita pelo `mongos` em 5.3.

## 5. Operações com várias chaves: `CROSSSLOT`

Tente gravar e ler duas chaves em um único comando:

```redis
MSET bdnr:ana_silva:sessao:demo02 "usuario102" bdnr:ana_silva:contador:visitas 0
MGET bdnr:ana_silva:sessao:demo01 bdnr:ana_silva:contador:acessos
```

Espere o erro `CROSSSLOT Keys in request don't hash to the same slot`. Comandos com várias chaves, como `MSET`, `MGET`, `DEL a b`, `SUNION` e transações `MULTI`/`EXEC`, exigem que todas as chaves estejam no **mesmo slot**. Estar no mesmo nó não basta: `contador:acessos` (9524) e `chamado:CH101` (6854) estão ambos em `redis-c2`, mas em slots diferentes, e também produzem o erro:

```redis
MGET bdnr:ana_silva:contador:acessos bdnr:ana_silva:chamado:CH101
```

## 6. Hash tags: agrupar chaves de propósito

Quando o nome contém `{...}`, só o trecho entre a primeira `{` e a `}` seguinte entra no cálculo do slot:

```redis
CLUSTER KEYSLOT bdnr:{ana_silva}:sessao:demo01
CLUSTER KEYSLOT bdnr:{ana_silva}:contador:acessos
CLUSTER KEYSLOT bdnr:{ana_silva}:chamado:CH101
```

As três respostas são iguais (6080 para `ana_silva`), porque o slot é calculado só sobre `ana_silva`. Agora as operações com várias chaves funcionam:

```redis
MSET bdnr:{ana_silva}:sessao:demo01 "usuario101" bdnr:{ana_silva}:contador:acessos 0
INCR bdnr:{ana_silva}:contador:acessos
MGET bdnr:{ana_silva}:sessao:demo01 bdnr:{ana_silva}:contador:acessos
```

As chaves `bdnr:ana_silva:contador:acessos` e `bdnr:{ana_silva}:contador:acessos` são diferentes. Mudar o nome de uma chave é criar outra chave, não mover a antiga.

A hash tag tem um custo: todas as chaves com a mesma tag ficam no mesmo slot e, portanto, no mesmo primário. Calcule o slot da tag de três colegas:

```redis
CLUSTER KEYSLOT bdnr:{bruno_lima}:x
CLUSTER KEYSLOT bdnr:{carla_souza}:x
CLUSTER KEYSLOT bdnr:{diego_alves}:x
```

Esses três exemplos caem em `redis-c3` (14650, 11229 e 11570). Com muitos alunos, as tags tendem a se espalhar pelos três primários. Com poucos valores de tag, ou com uma tag fixa para todos, a carga se concentra:

| Escolha de tag | Efeito |
|---|---|
| Uma tag por aluno, `{ana_silva}` | Operações com várias chaves do mesmo aluno funcionam; alunos diferentes se espalham pelos nós |
| Uma tag para todos, como `bdnr:ranking:{global}` | Tudo em um slot e um primário; os outros dois ficam ociosos |
| `{}` vazia | Ignorada: o slot é calculado sobre o nome inteiro |

É o mesmo raciocínio da cardinalidade e da chave hashed do material 5.3: poucos valores distintos concentram dados e acessos em uma parte do cluster.

## 7. Redirecionamento MOVED e failover no Redis Cluster

No Redis Cluster, os dados são distribuídos entre diferentes nós. Para compreender seu funcionamento, precisamos distinguir dois mecanismos:

- **Redirecionamento:** encaminha o cliente ao nó responsável pela informação.
- **Failover:** permite que uma réplica assuma o papel de um primário que ficou indisponível.

### 7.1. Como o Redis identifica o nó responsável por uma chave?

O Redis Cluster divide o espaço de chaves em **16.384 slots**, numerados de 0 a 16.383. Cada chave é associada a um desses slots por meio de um cálculo de hash, e cada nó primário fica responsável por uma parte dos slots.

Assim, para localizar uma informação, a aplicação precisa alcançar o primário responsável pelo slot da chave.

| Elemento | Papel no cluster |
|---|---|
| Chave | Identifica o dado que será acessado. |
| Slot | Determina a partição à qual a chave pertence. |
| Nó primário | Atende às operações sobre os slots sob sua responsabilidade. |
| Réplica | Mantém uma cópia dos dados de um primário e pode substituí-lo em caso de falha. |

**Exemplo conceitual:** a chave de um contador pertence a um slot atendido pelo nó B. Se o cliente enviar a consulta ao nó A, será necessário direcioná-lo ao nó B.

### 7.2. O que significa a resposta MOVED?

A resposta **MOVED** informa que o comando foi enviado a um nó que não é responsável pelo slot daquela chave. Ela indica o slot e o endereço do nó ao qual o cliente deve enviar o comando.

Isso não significa que a chave foi movida naquele momento. O cliente pode simplesmente ter consultado o nó errado ou estar usando informações antigas sobre a distribuição dos slots.

O fluxo é o seguinte:

1. O cliente envia uma consulta ao nó A.
2. O nó A identifica que o slot da chave pertence ao nó B.
3. O nó A devolve uma resposta MOVED com o endereço do nó B.
4. Um cliente com suporte ao Redis Cluster utiliza essa informação para reenviar a consulta ao nó correto e atualizar seu conhecimento sobre o cluster.

**O nó A não encaminha a consulta por conta própria: o redirecionamento é tratado pelo cliente.**

Por isso, a aplicação deve utilizar uma biblioteca com suporte ao Redis Cluster. Um cliente sem esse suporte pode apenas apresentar a resposta MOVED como um erro, sem continuar a operação.

Na comparação com o MongoDB, o `mongos` atua como um componente de roteamento entre a aplicação e os shards. No Redis Cluster, o cliente normalmente conhece a distribuição dos slots e se comunica diretamente com os nós responsáveis.

### 7.3. O que é failover?

O **failover** é o processo de substituição de um nó primário indisponível por uma de suas réplicas.

Durante o funcionamento normal, o primário recebe as escritas e transmite as alterações para suas réplicas. Se ele falhar, o cluster pode promover uma réplica elegível a novo primário, desde que existam as condições necessárias para a eleição.

| Momento | Primário original | Réplica |
|---|---|---|
| Funcionamento normal | Atende às operações e transmite alterações. | Recebe as alterações e mantém uma cópia dos dados. |
| Falha do primário | Fica indisponível. | Pode ser escolhida para assumir seus slots. |
| Após o failover | Permanece indisponível até se recuperar. | Atua como novo primário e atende às operações. |
| Retorno do nó original | Normalmente passa a atuar como réplica do novo primário. | Continua como primário. |

**Exemplo conceitual:** o nó B atende aos chamados de determinado intervalo de slots, enquanto o nó C mantém uma réplica desses dados. Se B ficar indisponível e C for promovido, C passa a atender às operações desse intervalo.

O retorno de B não significa que ele recuperará automaticamente o papel de primário. Ele pode voltar como réplica de C e sincronizar seus dados com o novo primário.

### 7.4. O sistema continua funcionando sem interrupção?

O failover melhora a disponibilidade, mas **não garante uma transição instantânea**.

O cluster precisa detectar a falha e realizar a eleição. Durante esse intervalo, algumas operações podem falhar temporariamente. Após a promoção, os clientes também precisam reconhecer o novo nó responsável pelos slots.

A recuperação depende de fatores como:

- Existência de uma réplica apta a assumir o primário.
- Comunicação entre os nós.
- Disponibilidade da maioria dos primários para autorizar a eleição.
- Capacidade do cliente de atualizar o mapeamento dos slots e restabelecer as operações.

Se um primário e todas as suas réplicas ficarem indisponíveis, os dados dos slots desse grupo não poderão ser atendidos. Dependendo da configuração de cobertura do cluster, isso pode impedir operações em todo o cluster.

### 7.5. Failover garante que nenhum dado será perdido?

Não. A replicação do Redis é **assíncrona**: o primário pode confirmar uma escrita ao cliente antes que ela tenha sido recebida pela réplica.

Considere esta sequência:

1. O primário recebe a alteração de um chamado.
2. O primário confirma a operação à aplicação.
3. Antes de transmitir a alteração à réplica, o primário falha.
4. A réplica é promovida, mas ainda possui a versão anterior do dado.

Nesse cenário, uma escrita confirmada pode ser perdida durante o failover.

Mecanismos como o comando `WAIT` permitem aguardar a confirmação de recebimento por réplicas e reduzir esse risco, mas não oferecem garantia absoluta contra perda de dados.

### 7.6. Relação entre os mecanismos

| Mecanismo | Problema que resolve | Limitação |
|---|---|---|
| MOVED | Informa ao cliente qual nó é responsável pelo slot de uma chave. | Exige que o cliente trate o redirecionamento. |
| Replicação | Mantém cópias dos dados em outros nós. | As cópias podem estar temporariamente atrasadas. |
| Failover | Permite substituir um primário indisponível. | Depende das condições do cluster e pode envolver interrupção temporária e perda de escritas recentes. |

Após um failover, o responsável por um conjunto de slots muda. Um cliente que ainda tente acessar o primário antigo precisará atualizar suas informações para se comunicar com o novo primário.

## 8. Limpeza

DEL bdnr:ana_silva:contador:acessos
